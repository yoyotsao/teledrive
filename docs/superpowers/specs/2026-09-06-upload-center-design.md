# TeleDrive 統一上傳中心設計規格

日期：2026-09-06  
狀態：已確認設計，待撰寫實作計畫

## 摘要

TeleDrive 將以單一、工作階段內持續存在的「上傳中心」取代目前由個別上傳批次直接覆寫畫面狀態的做法。所有後續拖放、檔案選擇及資料夾上傳都追加到同一個佇列；使用者可以查看、搜尋及篩選本次頁面工作階段內的全部項目，不再只看得到資料夾上傳的最後 100 筆。

上傳中心預設將失敗項目置頂、進行中項目其次，並收合已完成項目。舊失敗不會因新一批上傳而消失。再次上傳同一個失敗檔案時，系統會沿用原列並標示新的嘗試次數，不產生重複列。影片預覽開啟時，上傳中心會縮成右上角的進度按鈕，避免遮住播放器。

本變更只調整前端狀態管理及顯示。二進位資料仍必須直接在瀏覽器與 Telegram CDN 之間傳輸；Python 後端只處理 SQLite 中繼資料，不得成為檔案代理。

## 背景與目前問題

目前的上傳資訊位於 `frontend/src/components/ChonkyDrive.tsx`：

- `uploadingFiles` 是單一陣列，但每次 `startUploadBatch()` 都用新批次整體取代它。較早與較新的非同步回呼會輪流寫回各自的陣列快照，造成列表跳動、內容互相覆蓋，視覺上像兩個批次列表。
- 資料夾上傳使用 `VISIBLE_MAX = 100` 的 rolling window；第 101 個項目加入時會移除最早一筆，因此無法查看全部檔案及早期失敗。
- 列表只有檔名、百分比與簡短狀態，沒有失敗總數、狀態篩選或搜尋。大量上傳時很難確認是否有失敗。
- 面板固定在右下角且使用高於預覽遮罩的堆疊層級。影片預覽開啟後，面板仍會蓋在播放器上。
- 上傳項目以檔名尋找及更新；同名檔案可能更新到錯誤的列。

## 目標

1. 所有上傳入口共用唯一的上傳中心及項目集合。
2. 新上傳只追加或重試，不得清除或覆蓋既有狀態。
3. 在合理的瀏覽器記憶體範圍內保存本頁面工作階段的全部上傳項目，並以虛擬捲動避免大量 DOM 節點。
4. 讓失敗數量與失敗檔案不需逐列掃描即可辨識。
5. 再次上傳相同的失敗檔案時沿用原列，不顯示兩列。
6. 影片預覽期間不遮擋播放器，但仍能看見整體進度及失敗徽章。
7. 維持現有上傳併發、去重、縮圖、Telegram 帳號分配及中繼資料註冊行為。
8. 所有驗證均自動化；不得以人工操作作為驗收依據。

## 非目標

- 不將上傳佇列或歷史寫入 SQLite、IndexedDB 或後端。
- 不支援重新整理頁面後續傳或恢復上傳中心紀錄。
- 不改變 Telegram 上傳協定、分段策略、併發數或重試策略。
- 不新增暫停、取消或手動重試按鈕；重新選取或拖入失敗檔案即代表重試。
- 不建立跨瀏覽器分頁共享的上傳中心。
- 不保留跨工作階段的永久活動紀錄。

## 使用者體驗

### 展開狀態

桌面版維持浮動面板形式，預設位於右下角。面板寬度為 360–420 px，高度不得超過視窗可用高度的 65%；項目區在固定高度內捲動。面板使用現有 `--td-*` 色彩變數、字體與圓角，不建立獨立視覺語言。

```text
┌ 上傳中心 ───────────────── 986 / 1000 ┐
│ 全部 1000｜進行中 8｜失敗 14｜完成 978 │
│ 搜尋檔名…                              │
├───────────────────────────────────────┤
│ × vacation-03.mp4       上傳失敗       │
│ × report.zip            註冊失敗       │
│ ↻ archive.part2         63%            │
│ ✓ photo-001.jpg         已完成         │
│            …可捲動查看全部…            │
├───────────────────────────────────────┤
│ 清除已完成與失敗                收合   │
└───────────────────────────────────────┘
```

標題顯示 `已結束數 / 總數`。已結束數包含成功與失敗，避免上傳失敗時整體進度永遠達不到總數。只要存在失敗，標題旁必須顯示紅色失敗數量。

### 狀態篩選與排序

面板提供四個篩選：

- **全部**：預設檢視。依序顯示失敗、進行中、已完成三組；已完成組預設收合。
- **進行中**：包含排隊、計算雜湊、上傳位元組及註冊中。
- **失敗**：只顯示失敗項目及其具體錯誤原因。
- **完成**：只顯示已成功完成的項目，不再套用「已完成組收合」。

狀態組間的順序固定為失敗、進行中、完成。失敗組內依最近失敗時間由新到舊排列；進行中組維持加入順序，避免進度更新時不停跳位；完成組依完成時間由新到舊排列。

搜尋比對檔名及相對路徑，不分大小寫。搜尋作用於完整項目集合，而不是只搜尋目前虛擬捲動已渲染的列。搜尋有內容時，自動顯示符合的完成項目，不受完成組收合狀態限制。

「全部」檢視在列表上方提供「顯示已完成（N）」切換控制；關閉時，完成列不進入虛擬列表。列表本身只呈現依上述規則排序後的檔案列，不插入不同高度的分組標題，確保 windowing 計算穩定。

### 項目列

每列至少顯示：

- 狀態圖示。
- 檔名；資料夾上傳中若有同名檔案，第二行顯示相對路徑。
- 上傳中顯示百分比；排隊、計算雜湊與註冊中顯示明確文字。
- 失敗時顯示短錯誤類別，例如「上傳失敗」、「縮圖失敗」或「註冊失敗」。完整錯誤訊息由列上的可鍵盤操作「詳細資訊」控制顯示在面板內固定的錯誤詳情區，不得只依賴 hover tooltip，也不得改變虛擬列表的列高。
- 曾重試的項目顯示「第 N 次嘗試」。第一次嘗試不顯示額外文字。

進度百分比只能前進；項目進入 `complete` 時固定為 100%。項目進入 `error` 時保留失敗前最後已知的百分比，不得重設為 0%，以便診斷失敗階段。

### 收合狀態

使用者可手動把面板收合成小型進度按鈕。按鈕顯示：

- 有進行中項目時：整體完成比例及剩餘項目數。
- 有失敗項目時：紅色失敗數量徽章。
- 沒有進行中或失敗項目時：完成圖示；使用者仍可展開查看工作階段紀錄。

第一次加入上傳項目時，如果沒有開啟檔案預覽，面板預設展開。使用者手動收合後，後續加入項目不得擅自重新展開；失敗只更新徽章，不搶走焦點。

整體完成比例以項目數計算：`floor((complete + error) / total * 100)`。失敗代表該次工作已結束，因此計入完成比例，但必須同時由紅色徽章揭露，不能讓 100% 被誤解為全部成功。剩餘項目數為所有 active 狀態的數量。

### 影片預覽

開啟影片預覽時：

1. 上傳中心立即切換成收合按鈕。
2. 收合按鈕固定在預覽畫面右上角的安全區域，不得覆蓋影片內容、關閉按鈕或下載按鈕。
3. 上傳與狀態更新持續進行，不因預覽而暫停。
4. 關閉影片後維持收合，不自動重新展開。

若上傳是在影片預覽期間首次開始，直接顯示收合按鈕，不先閃現展開面板。本規格不改變圖片、PDF、音訊或文字預覽的上傳中心行為。

### 行動裝置

窄於 640 px 時，展開狀態改為底部 sheet，左右各保留 8 px 安全間距，最大高度為 60vh。收合按鈕不得遮住主要工具列或預覽控制。所有篩選可水平捲動，但不可截斷失敗數字。

## 統一狀態模型

### 上傳項目

前端應使用下列概念模型；實作可使用 TypeScript discriminated union，使各狀態只能攜帶有效欄位：

```ts
type UploadStatus =
  | 'queued'
  | 'hashing'
  | 'uploading'
  | 'registering'
  | 'complete'
  | 'error';

type UploadErrorStage = 'hash' | 'thumbnail' | 'telegram' | 'register';

interface UploadItem {
  id: string;
  name: string;
  relativePath: string;
  targetFolderId: string | null;
  size: number;
  lastModified: number;
  provisionalIdentity: string;
  contentHash: string | null;
  status: UploadStatus;
  progress: number;
  attempt: number;
  errorStage: UploadErrorStage | null;
  errorMessage: string | null;
  createdAt: number;
  updatedAt: number;
  completedAt: number | null;
}
```

`id` 是畫面列與所有非同步更新使用的穩定識別碼。任何更新不得再以檔名尋找列。

`targetFolderId` 與 `relativePath` 是重試合併判定的一部分。同一內容上傳到不同目的資料夾代表不同工作，不得合併成一列。

### 佇列狀態

統一佇列至少包含：

```ts
interface UploadQueueState {
  itemsById: Record<string, UploadItem>;
  order: string[];
  filter: 'all' | 'active' | 'error' | 'complete';
  query: string;
  completedCollapsed: boolean;
  panelMode: 'expanded' | 'collapsed';
}
```

所有批次只能送出針對項目 ID 的動作，例如 `enqueue`、`setHashing`、`setProgress`、`setRegistering`、`complete`、`fail` 與 `retry`。不得由某一批次以整個陣列呼叫 `setUploadingFiles([...batchResults])`。

計數、分組、搜尋結果及整體百分比均由 selector 從單一狀態計算，不另存容易失去同步的 `uploadTotals`。

### 狀態轉移

```text
queued → hashing → uploading → registering → complete
   │         │          │           │
   └─────────┴──────────┴───────────┴──→ error

error → queued    （重新選取相同失敗檔案）
```

去重命中時可以從 `hashing` 直接進入 `registering`；資料夾快速判定已存在時可以從 `queued` 或 `hashing` 直接進入 `complete`。無論走哪條路徑，都必須透過同一組項目 ID 更新動作。

## 相同檔案與重試規則

### 身分判定

檔案剛加入、內容雜湊尚未算出時，使用以下 provisional identity：

```text
targetFolderId + relativePath + name + size + lastModified
```

`relativePath` 是目的資料夾內、不含檔名的相對目錄路徑；直接上傳單一或多個檔案時為空字串。資料夾上傳尚未完成內層資料夾建立時，`targetFolderId` 使用該次上傳的根目的資料夾 ID，並由 `relativePath` 區分內層位置。

取得現有 `hashFileBounded()` 結果後，使用以下 canonical identity：

```text
targetFolderId + relativePath + contentHash + size
```

內容雜湊優先於 provisional identity。相同檔名但雜湊不同的檔案必須保持為不同項目。相同內容但目的資料夾或資料夾內相對路徑不同，也必須保持為不同工作。

### 再次加入時的行為

當使用者再次選取或拖入檔案：

| 現有項目狀態 | 身分相同時的行為 |
|---|---|
| `queued` / `hashing` / `uploading` / `registering` | 不新增、不重啟；聚焦既有項目並保持原進度。 |
| `error` | 沿用既有 `id`；`attempt += 1`，清除錯誤，狀態回到 `queued`，以新的 `File` 物件重跑完整流程。畫面全程維持一列。 |
| `complete` | 建立新項目；這代表使用者主動發起新的上傳工作，實際位元組是否省略仍交由既有內容去重流程決定。 |

如果 provisional identity 相同，但後續內容雜湊證明檔案不同，佇列必須保留原失敗項目，並為新內容建立新的項目。不得把原失敗紀錄改寫成另一個檔案的結果。

若使用者已清除舊失敗項目，之後再次加入相同檔案時會建立新列，`attempt` 從 1 開始。

### 同一批次中的重複內容

既有 `claimedHashes` 仍負責避免同一批次重複上傳位元組。上傳中心的項目身分與 Telegram 位元組去重是兩個不同概念：不同路徑或不同目的資料夾的項目可以各有一列，但仍可共用已上傳的 Telegram parts 並分別註冊中繼資料。

## 清除與保留

- 項目只保留在目前頁面工作階段的記憶體中。
- 新批次不得自動清除任何既有項目。
- `error` 項目必須持續保留，直到使用者清除、成功重試或重新整理頁面。
- 「清除已完成與失敗」只移除 `complete` 與 `error`；所有 active 狀態必須保留。
- 若存在 active 項目，關閉控制等同收合，不得丟棄進度列。
- 沒有 active 項目時，使用者可清除所有 terminal 項目並讓上傳中心消失。

## 虛擬捲動與效能

狀態中保留全部輕量 `UploadItem`，但不得為全部項目同時建立 DOM 列。列表採固定列高的 windowing：根據 `scrollTop`、viewport 高度與列高計算可見索引，上下各加入少量 overscan，並以頂部及底部 spacer 維持正確捲動高度。

本設計不新增虛擬列表套件。視窗計算應放在獨立、可單元測試的純函式中。篩選、搜尋或分組改變時必須校正 scroll offset，避免空白 viewport。

為避免高頻進度事件造成整個檔案瀏覽器重繪：

- 上傳佇列與上傳中心拆成獨立元件及 hook/reducer。
- 百分比相同的更新直接忽略。
- 畫面進度更新最多每個 animation frame 合併一次；實際上傳 callback 不受節流影響。
- `File`、Blob 或位元組資料不得存入 React 顯示狀態。執行中的 `File` 參照由上傳工作層持有，完成後釋放。

## 元件與責任邊界

### `frontend/src/lib/uploadQueue.ts`

- 定義 `UploadItem`、狀態、reducer actions 與 selectors。
- 產生 provisional/canonical identity。
- 決定加入、忽略、重試或拆成新項目。
- 實作篩選、搜尋、排序、計數及整體進度計算。
- 不依賴 React、GramJS、API client 或 DOM。

### `frontend/src/hooks/useUploadQueue.ts`

- 包裝 reducer，提供穩定的項目 ID 導向操作。
- 合併高頻進度更新。
- 保存 active item ID 到 `File` 工作參照的對應；terminal 狀態後釋放參照。
- 對 `ChonkyDrive` 暴露加入檔案、更新階段、完成、失敗與清除介面。

### `frontend/src/components/UploadCenter.tsx`

- 呈現展開面板、收合按鈕、計數、篩選、搜尋及清除控制。
- 只消費 queue snapshot 與操作 callback，不啟動任何上傳。
- 接收 `isVideoPreviewOpen: boolean` 並套用預覽避讓規則。
- 保存目前選取的錯誤詳情 ID，並在列表外的固定區域顯示完整錯誤，避免改變虛擬列高。
- 提供穩定的 `data-testid` 與無障礙名稱供 Playwright 驗證。

### `frontend/src/components/VirtualUploadList.tsx`

- 只渲染 viewport 及 overscan 範圍。
- 保持固定列高，提供正確的總捲動高度。
- 不持有上傳業務狀態。

### `frontend/src/components/ChonkyDrive.tsx`

- 保留拖放、選擇檔案、資料夾走訪、雜湊、Telegram 上傳及註冊流程。
- 將 `startUploadBatch()` 與 `uploadFolder()` 中的整體陣列替換改成 queue item ID 更新。
- 移除 `VISIBLE_MAX`、`visibleFiles`、`uploadTotals` 及依檔名更新列的邏輯。
- 將目前 `previewFile` 是否存在傳給上傳中心，用於自動收合。

不需要修改後端 API、資料庫 schema、Service Worker 或 Telegram 上傳函式。

## 錯誤處理

所有失敗都必須保存原始錯誤訊息，並映射為使用者可理解的階段：

| 階段 | 畫面短標籤 | 範例 |
|---|---|---|
| `hash` | 無法讀取檔案 | 檔案在選取後被移動或瀏覽器失去存取權。 |
| `thumbnail` | 縮圖處理失敗 | 可解碼媒體未能產生必要縮圖。 |
| `telegram` | 上傳失敗 | Telegram 連線中斷、限制或 part 上傳失敗。 |
| `register` | 註冊失敗 | 位元組已送到 Telegram，但 SQLite 中繼資料註冊失敗。 |

錯誤文字不得只寫「失敗」。未知例外顯示「上傳失敗」並保留安全處理後的原始訊息。錯誤資訊不得包含 session string、access hash、JWT 或其他憑證。

重新上傳失敗項目會重跑完整流程；本規格不要求從失敗百分比續傳，也不要求刪除先前可能留在 Telegram 的孤兒訊息。

## 無障礙

- 展開面板使用具名稱的 region，例如 `aria-label="上傳中心"`。
- 篩選使用可鍵盤操作的 tabs 或等價控制，並暴露選取狀態。
- 收合按鈕的 accessible name 包含進行中與失敗數量。
- 新增失敗時透過單一摘要 live region 宣告，例如「2 個檔案上傳失敗」；不得對每個百分比更新使用 live region。
- 顏色不是唯一狀態訊號；圖示旁必須有文字或 accessible label。
- 所有控制提供明顯的鍵盤 focus 樣式，並尊重 `prefers-reduced-motion`。

## 自動驗證

### 單元測試

以 Vitest 驗證純狀態與 windowing 邏輯：

1. 新批次追加後仍保留舊批次的成功、進行中與失敗項目。
2. 不同批次的非同步 action 只更新指定 ID，不會覆蓋其他項目。
3. 同名不同 ID 的進度互不影響。
4. 相同失敗檔案重新加入時保持一個 ID、`attempt` 加一並清除錯誤。
5. 相同 provisional identity 但不同內容雜湊時拆成兩個項目，原失敗資料不遺失。
6. 相同 active 檔案再次加入時不新增項目。
7. 同一內容但不同目的資料夾或相對路徑不合併。
8. 清除動作只移除 terminal 項目。
9. 失敗、進行中、完成的排序與四種篩選符合規格。
10. 搜尋能找到虛擬 viewport 外及已收合完成組內的項目。
11. windowing 計算在列表頂部、中段、底部及篩選後均回傳正確範圍。

### Playwright

新增 isolated Playwright 規格，使用既有 fake drive 與 route interception，不依賴人工測試：

1. 加入至少 150 個檔案後，可透過搜尋找到第 1 個、第 100 個及最後一個項目，證明沒有 100 筆上限。
2. 第一批仍有延遲中的項目時加入第二批，畫面只有一個上傳中心，總數為兩批總和，且第一批狀態不被覆蓋。
3. 製造註冊失敗後再次選取相同內容，失敗列直接轉為第 2 次嘗試，DOM 與狀態中都只有一列。
4. 同名但內容不同的兩個檔案顯示兩列並各自更新。
5. 失敗項目置頂；切換失敗篩選後只看見失敗項目及具體原因。
6. 清除已完成與失敗後，進行中的列仍存在。
7. 開啟影片預覽後，展開面板消失、收合按鈕出現，按鈕與影片及預覽控制的 bounding boxes 不重疊。
8. 關閉影片後維持收合；上傳完成與失敗徽章仍持續更新。
9. 在窄螢幕 viewport 驗證底部 sheet 不超出畫面，篩選及清除控制可用鍵盤操作。

既有 `upload-pipeline.spec.ts`、`upload-refresh.spec.ts`、上傳 dedup smoke tests 及前端 build 必須繼續通過。最終驗收依專案規範使用 Playwright MCP 執行，不接受以人工瀏覽器操作代替。

## 驗收標準

- 任意時刻只存在一個上傳中心。
- 第二次及之後的拖放會追加到同一個佇列，不會替換或產生另一份列表。
- 本頁面工作階段內的全部項目皆可透過捲動、篩選或搜尋找到。
- 大於 100 筆時不刪除早期項目，也不為每筆建立常駐 DOM 節點。
- 失敗總數始終可見；失敗列預設優先於進行中及完成列。
- 新批次不會清除舊失敗。
- 相同失敗檔案再次上傳時畫面維持一列並顯示增加後的嘗試次數。
- 相同 active 檔案不會重複排入；同名不同內容不會被錯誤合併。
- 影片預覽期間，上傳 UI 不遮住播放器或預覽控制。
- 清除操作永遠不移除進行中的工作。
- 不新增任何讓檔案位元組經過 Python backend 的路徑。

## 已排除方案

### 每批各自一張卡片

這會延續使用者已遇到的多列表問題，並使跨批次失敗統計與搜尋更困難，因此不採用。

### 只提高 `VISIBLE_MAX`

把 100 改成更大的固定數字仍會遺失資料，也會讓 DOM 數量隨上限成長；無法滿足「全部可查」及大量上傳效能需求。

### 完成後自動清空

大量上傳後使用者無法確認哪些檔案失敗，也會讓下一批覆蓋上一批問題以另一種形式存在，因此 terminal 項目只由使用者清除。

### 將上傳紀錄交給後端保存

此需求只涉及瀏覽器工作階段的 UI 狀態。新增後端持久化會擴大資料模型與清理責任，且不解決頁面內佇列互相覆寫的根因。
